## Release-process facts worth keeping
- `.github/workflows/release.yml` triggers only on tags matching `v[0-9]+.[0-9]+.[0-9]+`; it builds the .deb, runs `smoke_test.sh` + `deb_selfsufficiency_test.sh` (needs Docker in CI), builds sdist, writes `SHA256SUMS.txt`, publishes via `softprops/action-gh-release`.
- **`scripts/build_deb.sh` reads the version from `pyproject.toml`** — no separate version variable to keep in sync there.
- **The site embeds the version** (`site/src/consts.ts` → `DEB_URL` points at `releases/download/v${VERSION}/...`). A version bump MUST include the site files or the deployed download link 404s. This is a gap the "version bump" instructions don't mention; the `test_version_consistency.py` only checks pyproject/`__init__`/CHANGELOG.
- Local Docker: daemon not started by default; `sudo -n dockerd &` works and `sudo -n docker` is the usable form (socket is root-owned). `xvfb`/`xvfb-run` had to be `apt-get install`ed — and it still doesn't enable local GUI tests: the `.venv` is **Python 3.13** while `gi`/PyGObject is only in the **system Python 3.12** (`/usr/lib/python3/dist-packages`), so `import gi` fails in the venv. GUI tests only run in CI's dedicated job.
